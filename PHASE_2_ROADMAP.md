# PetPro Connect — Phase 2 Roadmap

*Created 2026-07-15 at founder direction. This is a **living document** — we add to it as development continues, using the same status legend and update habits as `ROADMAP.md`. The Phase 1 tracker (`ROADMAP.md`) remains the source of truth until the Week 8 demo ships; **nothing in this file starts before then** unless the founder explicitly pulls an item forward.*

---

## How This Works

Phase 2 is organized into **workstreams** instead of fixed weeks, because scope will keep growing. Each workstream ends with a **QA checkpoint** and the phase has scheduled **security reviews** (Workstream Q) — a workstream isn't done until its gate passes. A proposed sequencing order is at the bottom; the founder re-prioritizes as we learn.

**Status legend** (same as `ROADMAP.md`): `[ ]` not started · `[x]` done · `[~]` in progress · `[!]` issue · `[d]` delayed — with a one-line note under any `[!]`/`[d]`.

**Ground rules carried over — these do not expire with Phase 1:**
- All `CLAUDE.md` hard constraints still apply: modular monolith, REST only, Stripe only, eSign via `IeSignProvider`, append-only events, signed-contract immutability, types live in `src/types/index.ts`.
- The four marketplace seams stay intact: typed accounts, event log, provider adapters, generic billing. Workstream X exists to *exercise* those seams, not bypass them.
- One feature fully working beats several half-done. Commit after each working feature.

## Workstream D — Account Lifecycle & Data Privacy (delete / deactivate)

> **Added 2026-07-19 at founder direction — data privacy and deletion is a first-class concern, not a backlog afterthought.** Detailed spec stays in `ROADMAP.md` → **P2-15**; this workstream schedules the build and its gates. It lands **early** because it's the seam **M-Connect's** Stripe Connect account depends on. (Test-data residue is handled separately by Workstream 0's test project — **not** by this; the earlier coupling was dropped when the test-data decision flipped.)

**Core principle (from the spec — do not violate):** a hard row delete is architecturally impossible *by design* — four FKs reference `accounts(id)` with no `ON DELETE` rule, and the `events` append-only trigger (Marketplace Seam 2 + a `CLAUDE.md` hard constraint) forbids deleting event rows. **Build it as deactivation + PII scrub, never row deletion.**

- [x] **Deactivation core:** set `status = 'deactivated'` (the enum value has existed unused since migration `001`); block login and reject the session in `requireAuth`. This is the seam — a reversible status flip, not a destructive op. — **DONE 2026-08-01** (`AccountService.deactivateAccount()`). `requireAuth` already 403'd any non-active account, so every live session dies on the flip; also added a status guard to `authenticateProfessional` so re-login is refused. Migration `024` adds `accounts.deactivated_at`.
- [x] **PII scrub:** null/redact the identifying columns on `accounts` (`email`, `phone`) so a "delete my data" request is satisfied while the immutable history keeps referring to a row that still exists (keep `id`). — **DONE 2026-08-01**, scope = **contact-only** (founder decision 2026-08-01, chosen over deep/minimal): scrub the *leaver's own* contact identifiers — `accounts.email` → unique tombstone (`deactivated+<id>@deleted.invalid`, since it's UNIQUE NOT NULL and can't be nulled), `accounts.phone` → null, plus the professional's `bio` / the owner's `address`. **Client records are NOT touched** — this honors the retain-clients decision below (retained clients are separate people with live portal access; wiping their `general_notes`/gate codes would degrade records the professional must keep). `professional_profiles.business_name` **and** `full_name` are kept so the portal can still name the walker as "deactivated".
- [x] **Supabase Auth user:** delete or disable the matching `auth.users` row, or a deactivated account can still authenticate (`AccountService.ts:61` already flags the orphan-auth-user case — this seam is known fiddly). — **DONE 2026-08-01**: deletes the auth user then nulls `accounts.auth_user_id`. Best-effort (logged on failure) because the status flip is the authoritative lockout; the deleted user also means dead tokens 401 at `getUser` before the status check even runs.
- [x] **Retention guardrails:** signed contracts (`generated_html` immutable once signed), invoices, and transactions must survive deactivation untouched — retention/legal value, and a hard constraint. — **DONE 2026-08-01**: the method never references those tables; e2e step 16 asserts the signed contract (status + `generated_html` intact) and invoice remain readable after deactivation.
- [x] **Connected-account link (M-Connect seam):** the Stripe Connect `account_id` is a **nullable, replaceable** link cleared on deactivation / relationship-termination — never hardwired into the payment path. M-Connect builds on this; deactivation must null it cleanly. — **DONE 2026-08-01**: migration `024` adds nullable `accounts.stripe_connect_account_id` (nothing populates it until Workstream M); deactivation nulls it; e2e plants a dummy id and asserts it's cleared.
- [x] **e2e cleanup path (convenience, not load-bearing):** deactivation gives the test suite a tidy way to retire accounts *within the test project*. — **DONE**: `accountService.deactivateAccount(id)` is idempotent and callable directly, so tests/cleanup can retire accounts.
- [x] **Client handling (DECIDED 2026-07-19 — retain, portal access unaffected):** a deactivated professional's client rows and their owners' portal login stay intact (orphan-but-retain — real people with signed agreements). Wherever the walker is surfaced to an owner, they **display as "deactivated"** rather than disappearing. — **DONE 2026-08-01**: `PortalService.overview()` returns a `professional.deactivated` flag (withholding the scrubbed email/phone, keeping business name); `portal.js` renders a "Deactivated — account closed" card instead of the contact details. Client rows are untouched; e2e asserts the owner still sees their retained client + the deactivated walker.
- [x] **QA checkpoint D:** deactivate a professional **and** an owner account → login blocked, session rejected, PII scrubbed, auth user gone → signed contracts / invoices / transactions still intact and readable → the professional's clients retained, their owners' portal login still works, and the walker shows as "deactivated" in the portal. — **DONE 2026-08-01** as **e2e step 16** (green locally; runs on push/PR in CI). Self-service surfaces: `POST /api/auth/deactivate` (professional, password-confirmed) + "Close my account" in the Profile tab; `POST /api/portal/deactivate` (owner, passwordless — the magic-link session is the proof).

## Workstream M — Mobile: Android-first native app

> **Founder direction 2026-07-19: build a real native app, Android first.** This supersedes the earlier PWA-first stance (a good mobile web app was going to come first, native only when a feature demanded it). The founder's original goal was an app for iOS **and** Android; the plan below gets there in phases. Phase 1 (the web app) is unchanged and remains the demo surface for now. iOS follows in **Phase 3** (below).

**Approach:** Capacitor wraps the existing web app (`public/`) into an Android shell — still one deployable, same backend. Native device features are Capacitor plugins called from the existing UI, pulled forward from the backlog.

**Why Android-first:**
- Android builds on the founder's **Windows** machine — no Mac needed. That constraint moves to Phase 3 with iOS.
- Google Play does **not** apply Apple's 4.2 "not just a website" wrapper rejection, so native features here are driven by walker value, not review-clearing. (Apple's 4.2 gauntlet re-enters in Phase 3.)

### M-Connect — Payment setup: "Get paid" (Stripe Connect / P2-6)
*Gap found 2026-07-19: the simplified onboarding has **no way for a professional to set up getting paid** — today all money routes to the platform (founder) Stripe account. Real walkers can't receive money until this exists, and Tap-to-Pay to a real walker's account depends on it.*
- [ ] **Stripe Connect Express** (founder decision 2026-07-19) — Stripe-hosted KYC/onboarding.
  - ⚠️ **Do not hardwire the connected account.** It must be disconnectable/changeable later — e.g. if the professional relationship is terminated — so build it behind the same seam as **Workstream D** (P2-15) account deactivation, not as a permanent one-time link. Storing the `account_id` is a nullable, replaceable link on the account, never an assumption baked into the payment path.
- [ ] Generate onboarding link, store connected `account_id`, handle the incomplete-onboarding (not-payout-ready) state.
- [ ] Route charges (Checkout **and** Tap-to-Pay) to the walker's connected account. `PaymentService` was built so Connect slots in without changing callers.
- [ ] **Pre-onboarding behavior = BLOCK** (**DECIDED 2026-08-29**). Until the connected account is payout-ready, card collection is **refused** — never a silent fallback to the platform account. Gate the invoice/charge surfaces on the not-payout-ready state from the item above, with the persistent Profile card as the route to finish. *Rationale: the fallback's cost isn't code, it's the platform holding money it doesn't own plus a manual remittance ledger — a payment-intermediary posture for a solo operator.*
  - ⚠️ **Accepted consequence — no manual payment path until Phase 3.** BLOCK removes the card route for a walker who isn't payout-ready, and there is no "mark as paid" for money taken outside Stripe: that's **P2-9**, which was raised as a pairing on 2026-08-29 and **deliberately left in Phase 3** by founder direction. So between signup and payout-ready, a walker has no way to record *any* payment, cash included — and `KNOWN_ISSUES.md` notes real walkers are handed cash constantly. Recorded here so it isn't re-litigated as a bug; revisit if real walkers hit the window.
- [ ] "Set up payments" step in the onboarding wizard (skippable) **plus** a persistent Profile card until complete.
  - **Founder confirmed 2026-08-08:** add this as an **optional** step in the signup process so a professional can set up accepting payments during onboarding (and skip to do it later). ✅ Already the plan — noting the explicit ask so it isn't re-derived.
  - ⚠️ **We never collect raw banking details ourselves.** With Stripe Connect Express (line above), bank account / tax ID / KYC are entered on **Stripe's hosted onboarding**, not a form in our app — we only store the returned `account_id`.
